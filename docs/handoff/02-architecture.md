## The feature-module registry

Rule (`CONTRIBUTING.md`, `docs/CONTRACTS.md`): a feature owns only its
`src/features/<area>/` folder, its tests and its fixtures. It contributes to
the app by exporting `feature: FeatureModule` from `index.tsx`. Shape
(`src/app/feature.ts`):

- `id`, `routes: { path, element }[]`, optional `nav` (static sidebar items with
  `order`), optional `navProvider` (a hook, called every shell render, for items
  that depend on a database read: Today's pinned views, the pipeline row named
  from the vocabulary), optional `commands` (`id`, `label`, `shortcut`,
  `aliases`, `whileTyping`, `keywords`, `group`, `run`), optional `overlays`
  (always-mounted dialogs rendered inside the shell providers), optional
  `onBoot` (idempotent, never allowed to throw the app down).
- `src/app/registry.ts` lists all thirteen in this order: today, schedule,
  records, data, leads, ai, settings, onboarding, recurring, templates, help,
  catalog, invoices. Registration order breaks ties (route matching, shortcut
  conflicts, palette order). It also holds app-level commands (undo, redo,
  toggle sidebar, refresh). `CONTRACTS.md` still says "all six"; the code has
  thirteen.
- Route order matters: wouter's `Switch` takes the first match, so
  `/invoices/new` is registered before `/invoices/:id`. A comment in
  `settings/index.tsx` says leads also registers `/settings/site`; the current
  `leads/index.tsx` does not, so that comment is stale.
- Sidebar shape comes from `NAV_GROUPS` (by route), not by number. `NAV_ORDER`
  values: today 10, views 15, contacts 20, companies 30, pipeline 40, services
  45, invoices 48, reports 50, schedule 58, tasks 60, reminders 65, import 70,
  trash 80, settings 90, help 95. Three features use literals instead
  (invoices 58, reminders 55, trash 85 in their own `index.tsx`); the group table
  makes that harmless.
- `onBoot` hooks that start timers: `leads` (lead poller), `data` (backup
  scheduler, duplicate scanner, trash purge sweep), `invoices` (billing
  schedule runner), `settings` (automations: registers the quote-sent listener,
  runs the overdue sweep on a 24 h beat). `schedule` and `recurring` have no
  `onBoot` because their questions are date queries.

Keys the shell binds (`src/app/shortcuts.ts`, `Shell.tsx`): one `keydown`
handler answers every registered `shortcut` and `aliases`. `mod` is Cmd on macOS
and Ctrl elsewhere. Typing in an input suppresses everything except commands
marked `whileTyping`. Cmd/Ctrl+K runs the command with id `search` (falls back
to the palette); Cmd/Ctrl+Shift+K is always the palette; Cmd/Ctrl+/ is a search
alias; Cmd/Ctrl+R is the app `refresh` command (`menu.rs` claims Cmd+R so the
web view never reloads).

## Data flow

```
screen (React) --> TanStack Query hook --> repository (src/db/repos/<entity>.ts)
      --> raw.query / raw.batch (src/db/client.ts) --> Tauri invoke
      --> Rust command (db_query, db_batch, ...) --> one rusqlite connection
      --> SQLCipher file  <workspace>/helix.db
```

Rules (`CONTRIBUTING.md`, `docs/CONTRACTS.md`, all enforced by review and
tests, not by the compiler):

- SQL lives only in repositories (`src/db/repos/*.ts`, 33 files including
  `_base.ts` and `_pickers.ts`). Screens and services never write SQL. Two
  exceptions worth knowing: `src/features/data/lib/exportRun.ts` builds its own
  read-only queries, and onboarding's `sampleData.ts` builds statements for its
  load and removal. Both go through `raw`, not around it.
- Rows come back from the pipe as arrays in select order. Every repository
  declares columns once (`Col[]` in `_base.ts`) and gets the aliased select list
  and row mapper from that. A join must alias every column; there is a regression
  test.
- Money is integer cents; tax is basis points; dates that are days are local
  `YYYY-MM-DD` strings; instants are ISO 8601 UTC strings. IDs are UUIDs
  (v7-shaped; `src/lib/ids.ts`).
- Soft delete on nearly every entity (`deleted_at`), timestamps `created_at` and
  `updated_at`. Tables that are exceptions: `lead_sync`, `change_log`,
  `automation_runs`, `document_items`, `document_sequences`, `schema_migrations`,
  `settings` (no soft delete).
- Zod validation in `create`/`update`; `ValidationError` messages use the owner's
  word for a deal via `src/lib/vocabulary.ts`.

### The Rust command contract

All commands are `#[tauri::command(async)]`, registered in
`src-tauri/src/lib.rs` (20 commands). Errors serialize as
`{ code, message }`; codes in `src-tauri/src/error.rs`: `DB_CLOSED`,
`DB_OPEN_FAILED`, `SQL_ERROR`, `TX_STATE`, `BACKUP_FAILED`, `IO_ERROR`,
`SECRET_ERROR`, `NET_ERROR`, `HTTP_STATUS`, `FTS_MISSING`.

| Module | Commands | Notes |
| --- | --- | --- |
| `db.rs` (1,109 lines) | `db_open`, `db_close`, `db_query`, `db_execute`, `db_begin`, `db_commit`, `db_rollback`, `db_batch`, `db_backup`, `db_info` | One `rusqlite::Connection` behind a mutex (not `tauri-plugin-sql`, whose pool can split a transaction across connections). `db_open` keys with SQLCipher first, then WAL, `foreign_keys=ON`, `busy_timeout=5000`, `temp_store=MEMORY`. `db_batch` is BEGIN..COMMIT in autocommit, SAVEPOINT..RELEASE inside a transaction. `db_backup` uses a second read-only connection and `VACUUM INTO`. `db_info` returns path, size (including WAL), fts5, SQLite version, `encrypted`, `cipherVersion`. |
| `secrets.rs` (871) | `secret_set`, `secret_get`, `secret_delete` | Kinds `anthropic` and `site` only; kind `dbkey` is refused with `SECRET_ERROR`. One keychain item per workspace, service `helix`, user `<workspaceId>:bundle`, holding a JSON object of kind to value; old per-kind items are folded in lazily. Unparseable items are never overwritten. Dev/test in-memory store: compiled out of release builds (`cfg(debug_assertions)`), opt-in with `HELIX_INSECURE_KEY_STORE=memory`. |
| `leads.rs` (1,069) | `leads_fetch` | See 01. Origin validated; no redirects; body cap 5 MiB read while streaming; JSON depth check before parse; page bounds (over-long id/email/phone rejects the page, display fields truncated); NUL and bidi override characters stripped; 401/403 bodies never echoed into errors or the log. |
| `files.rs` (401) | `copy_in`, `app_paths` | `copy_in(src)` copies into `<workspace>/attachments/<uuid>.<ext>`; Rust chooses the destination; refuses over 50 MiB (`MAX_ATTACHMENT_BYTES`). |
| `backups.rs` (266) | `backup_mirror` | Makes `<chosen folder>/Helix backups/<workspaceId>` hold exactly the `.db` files of the workspace's backups folder; only deletes `.db` files the source no longer has; refuses a destination inside the workspace. |
| `recovery.rs` (478) | `recovery_key_reveal`, `workspace_adopt_backup` | Format `HLX1-` plus 16 groups of 4 hex characters. `workspace_adopt_backup(sourcePath, recoveryKey)` proves the key opens the file, then copies it into a NEW workspace and stores the key under a Rust-minted id; any failure removes what it wrote. |
| `disk.rs` (392) | `disk_encryption_status` | `fdesetup` on macOS; `manage-bde` with a WMI fallback on Windows; 5 s timeout; `encrypted` is `null` when unknown, never a guess. |
| `menu.rs` (240) | none (attaches the app menu) | Custom items carry registry command ids or `nav:` routes and are emitted to the web view as a `menu` event, handled by `src/app/menu.ts`. Undo and Redo are custom, not predefined, so they can reverse a pipeline move. Two ids are handled in Rust (bring windows forward, open the issue tracker). |
| `error.rs`, `lib.rs`, `main.rs` | none | Error type; plugin and command registration, log plugin, single-instance and window-state plugins. |

Param binding: JS sends `null | number | string | boolean | Uint8Array`;
booleans bind as 0/1.

Capabilities (`src-tauri/capabilities/default.json`): frontend filesystem access
only inside the app data folder; dialog open and save; opener limited to `https://*`,
`mailto:`, `tel:`, `sms:` URLs and paths under `$APPDATA/workspaces/**`; http only to
`https://api.anthropic.com/*`; window drag and maximize; log; window-state.
CSP in `tauri.conf.json`: `default-src 'self'`, `connect-src 'self' ipc:
http://ipc.localhost`, no objects, no framing. Asset protocol scope:
`$APPDATA/workspaces/**/attachments/**` (thumbnails). Everything else (SQLite, the
lead poll, the keychain, attachment copies) runs behind a Rust command where the
path or origin is chosen in Rust.

## Data on disk

Application data folder (`app_paths().appData`):

- macOS `~/Library/Application Support/com.clearpathdigital.helix/`
- Windows `%APPDATA%\com.clearpathdigital.helix\`

Layout:

```
<appData>/
  helix.json                      app registry (not encrypted): workspaces list,
                                  lastOpened, theme, density, sidebar {width, collapsed}
  logs/helix*.log                 tauri-plugin-log, level Info, 4 MiB max per file,
                                  KeepSome(7), files older than 7 days swept on launch
  workspaces/<workspaceId>/
    helix.db                      SQLCipher database (+ helix.db-wal, -shm while open)
    backups/<ISO>-<reason>.db     encrypted backups (dashes in the time part)
    attachments/<uuid>.<ext>      copied-in files, plain
    documents/                    generated quote and invoice PDFs, plain
```

- `helix.json` is validated by `registrySchema` (`src/app/appSettings.ts`); a file
  from an older build parses with defaults; in a plain browser (the e2e build) it
  is held in memory. The workspace id is the name of the folder that holds
  `helix.db`; the keychain, `leads_fetch` and `backup_mirror` all derive it that
  way.
- Encryption (D18): every workspace file and every backup is SQLCipher. Key: 32
  bytes from the OS CSPRNG, stored as 64 hex characters, created on first open,
  held only in the OS keychain (bundle item above), applied with the raw-key form
  `PRAGMA key = "x'<hex>'"` as the first statement (no passphrase KDF cost). It
  never crosses IPC except through `recovery_key_reveal`, which answers only for
  the open workspace, on the owner's request. It is never written to SQLite,
  `helix.json` or the log. A plaintext workspace from before D18 is converted in
  place on first open (export via `sqlcipher_export`, verify, set aside as
  `<iso>Z-pre-encryption.db`, deleted by the first later open that succeeds).
  `db_open` refuses an encrypted file with no key in the keychain rather than
  minting a new key.
- Recovery key: shown in Today's card until the owner confirms they kept it, and
  in Settings, Backups. It is the only way to open a backup on another machine
  ("Open a backup from another machine" uses `workspace_adopt_backup`).
  Restoring a backup is a plain file copy over `helix.db` plus `db_open`; a backup
  cannot be opened in place from `backups/` because the id comes from the parent
  folder.
- Backups (`src/features/data`): on launch if the last one is over an hour old,
  then every 6 hours while open (`BACKUP_MIN_GAP_MS` 1 h, `BACKUP_INTERVAL_MS`
  6 h in `lib/retention.ts`), also before every migration (`pre-migration`), every
  import, and every restore (`pre-restore`). Retention (`planRetention`): keep
  everything from the last 24 hours, then the newest of each local day for 30
  days, always keep the single newest, never drop an unparseable name. Timers skip
  a tick while an import or restore holds the write lock.
- Second copy: `backupCopyDir` setting (per workspace) chooses a folder; after
  every successful backup `backup_mirror` makes it match. Failure is reported
  separately from the backup's own result.
- Logs: `helix.log` files in `<appData>/logs`. Diagnostics has "Copy log" and
  "Reveal data folder" actions. The log does not name customers (a 0.2.0 copy claim).
- Plain files by design (a stated limit in the copy): attachments, `documents/`
  PDFs, exports, saved statements, `.ics` files. Full-disk encryption covers them;
  Diagnostics shows `disk_encryption_status`.

## Frontend boot sequence

`src/app/boot.ts` (the same sequence runs again on every `db_open`: launch,
restore, workspace switch):

1. `app_paths`, read `helix.json`, create the first workspace if none exists.
2. `raw.open(<workspace>/helix.db)`. Failure classes each get a full-screen
   message (`BootScreens.tsx`): `DbOpenError`, `SecretStoreError` (keychain
   denied; its own headline), `Fts5MissingError`, `MigrationError`,
   `NewerSchemaError` (an older build refuses a workspace a newer build migrated).
3. `migrate()` (blocks first paint). Then `seedWorkspace()` (idempotent: one
   pipeline with six stages New, Contacted, Quoted, Scheduled, Won, Lost with 14
   quiet days on the first four; sources Website, Referral, Import, Manual).
4. Clear the TanStack Query cache and the undo stack. Compute the onboarding
   gate.
5. Paint (onboarding or Today). After first paint, each feature's `onBoot` runs.

A switch or restore closes and reopens the file; for that window every read
answers `DB_CLOSED`, and `beginDbTransition(label)` in `src/db/client.ts` names
the window so the top bar shows a quiet line ("Switching workspace...").

## The query cache rules

`src/app/queryClient.ts`: `staleTime: 0`, `gcTime` 5 minutes,
`refetchOnWindowFocus: true`, `refetchOnReconnect: false`, `retry: false`.
`src/app/refresh.ts`: the shell invalidates every query on each route change
(not on first render) and provides the `refresh` command ("Refresh this page",
mod+R, View menu, palette). The cache is cleared after every `db_open`. Query
keys are centralized in `qk` in `queryClient.ts`. Rule: a feature must not set a
long `staleTime` on its own queries. Reads are local and cheap; a stale number
on screen is the bug the owner reported (commit 2e035c6).

## The write lock

`src/db/writeLock.ts`. Every repository write goes through `withWrite(fn, label)`,
which queues callers behind one lock. `withTransaction(fn)` is `withWrite` plus
`raw.begin` / `commit` / `rollback`. The lock is NOT reentrant: a repository write
function must never call another repository's write function (the inner call queues
behind the outer and both wait forever). Need several writes together? Build
statements (`createStatements`, `changeLogStatement`, `systemStatement`, and so on)
and send one `raw.batch`, or do reads-only calls inside one `withTransaction`. The
lead poller, the import, merge, sample data load and automations all follow this.
`writeState` (`busy`, `label`, `queued`, `transition`) drives the top bar.
`pauseTimers()` / `timersPaused()`: import, merge and restore pause the background
timers (backup, poll, duplicate scan, purge sweep, invoice runner, automation
sweep skip that tick and retry after a minute). A concurrent-writer bug (F-OPS-12,
a `txDepth` shortcut that let an unrelated writer join another transaction) was
fixed in the launch round; see the tests under `tests/repo/leads/pollerRace.test.ts`.

## Undo and change_log

- `change_log` (table): one row per repository write with `op` in create, update,
  delete, restore, merge; `before_json`, `after_json`, `batch_id`, `actor_id`
  (always `owner`). Written in the same batch as the row it describes. Bounded to
  90 days (`CHANGE_LOG_RETENTION_DAYS`, swept daily by `purgeSweep.ts`).
- `undoBatch(batchId)` / `redoBatch(batchId)` (`src/db/changeLog.ts`) replay a
  batch. Only entity types in `TABLE_FOR_ENTITY` are replayable (17: contact,
  contact_phone, contact_email, company, pipeline, stage, deal, deal_stage_event,
  activity, task, tag, tag_link, custom_field, custom_value, attachment, source,
  saved_view). Documents, payments, products, templates, reminders and merges are
  not on the Cmd+Z stack. Payments have their own `payments.restore`; a merge has
  `merge.reverse(mergeId)` (30-day window, `MERGE_REVERSAL_DAYS`).
- Soft delete logs `before {deletedAt: null}` / `after {deletedAt}` with no `id`;
  hard delete logs the whole row with `id` (undo re-inserts it); `purgeRow` logs no
  `before`, so a purge cannot be undone (by design).
- The app undo stack (`src/app/undo.ts`): in memory only, `UNDO_LIMIT = 20`, cleared
  on every `db_open`. Delete toasts offer a 10 second undo (`toast.undo` default
  10000 ms). Cmd/Ctrl+Z and Cmd/Ctrl+Shift+Z; a text field keeps its own undo while
  typing. The Trash screen is the 30-day answer for a delete.

## Search

Index by triggers, not by code (`drizzle/0001_search.sql`): `search_docs`
(`rowid`, `entity_type`, `entity_id`, `text`, unique on entity) feeds `search_index`,
an FTS5 external-content table (`tokenize='unicode61 remove_diacritics 2'`). 21
triggers on contacts, contact_phones, contact_emails, companies, deals and
activities keep it current; a soft delete removes the row from the index, a restore
brings it back, and changing a phone or email rebuilds its contact. Payments and
documents are not indexed (documents are reached through their deal or customer).
`src/db/repos/search.ts` turns user input into a prefix query without
interpolating it, joins back to `search_docs`, groups by type for the palette. Perf
budget: median under 50 ms at 10,000 contacts (`tests/repo/today/search10k.test.ts`;
last local run medians 0.04 to 0.28 ms).

## Migrations

- Files `drizzle/0000_init.sql` to `0009_visit_note.sql`, ordered by
  `drizzle/meta/_journal.json` (10 entries, idx 0 to 9). Forward-only; there are no
  down migrations.
- `src/db/migrator.ts`: reads applied versions from `schema_migrations`. If it names
  a version this build's journal does not know, `NewerSchemaError` is thrown before
  anything else runs (no PRAGMA, no backup). If any are pending: backup
  `pre-migration`, `PRAGMA foreign_keys = OFF` (outside any transaction), for each
  pending file split on `--> statement-breakpoint`, append the
  `INSERT INTO schema_migrations` row as the last statement, send the whole file as
  ONE `db_batch`, then `foreign_key_check`, then `foreign_keys = ON`. A failure rolls
  the file back, leaves the database untouched and carries the backup path
  (`MigrationError`). SQL is bundled through Vite `?raw` imports, so no filesystem
  access is needed at runtime.
- Snapshot chain note: drizzle-kit snapshots exist for `0000` to `0005` and `0009`
  only. `0006_payments`, `0007_visits`, `0008_automations` and `0009_visit_note` were
  written by hand during the launch round, so the chain stopped at `0005`;
  `drizzle/meta/0009_snapshot.json` (commit bc537ce) was generated from the current
  `schema.ts` and re-baselines the chain so `npx drizzle-kit generate` reports no
  schema changes. Its `prevId` points at the `0005` snapshot. The 33 tables in the
  `0009` snapshot are the ones defined in `src/db/schema.ts`; the FTS tables
  (`search_docs`, `search_index`) and the five report views are custom SQL and not in
  any snapshot. When adding a migration: change `schema.ts`, run
  `npm run drizzle:generate`, check that the generated SQL matches any hand edits,
  and add tests (`tests/repo/migrations.test.ts` and the backfill tests show the
  pattern: seed a workspace at the previous migration, run the new one, compare).
- Data-changing migrations so far: `0005_lead_dedup` (soft-deletes later duplicates
  sharing an `external_id`, keeps the oldest, then adds a partial UNIQUE index);
  `0006_payments` (backfills one payment per already-paid invoice so Collected does
  not read $0 after upgrade); `0008_automations` (seeds three rows).

## Other seams worth knowing

- Vocabulary: the database always says `deals` and `stages`; labels come from the
  `vocabulary` setting (`deals` | `jobs` | `quotes`) through `src/lib/vocabulary.ts`
  (pure) and `useVocabulary()` in `src/app/vocabulary.ts`.
- Settings: `settings(key, value_json)` typed by a registry in
