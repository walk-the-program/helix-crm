## What this is

Helix CRM is an open-source desktop CRM for solo trade and service business owners
(landscapers, dentists, med spas, home services, venues, gyms, churches, restaurants:
the nine trades ClearPath sells websites to). It runs on Mac and Windows, keeps all data
in a local SQLite file, needs no account and no cloud, and imports from a spreadsheet
or any other CRM in five minutes. Leads from a ClearPath-built website land in it
automatically. AI is optional, bring-your-own-key, and off by default.

It is not AI-first. It is competent first. Walker's words: "it just needs to be
competent... a product that I want to use... open-source CRM could be cool."

The two-sentence test for every screen: the owner does not want a CRM. He wants to
not lose a lead and to remember what he promised.

The existing ClearPath pipeline tool at `ClearPath Sites/crm/` stays as it is for
outreach. Helix is a separate codebase. Its visual direction is a reference only.

## Landscape (three layers)

**Layer 1, tried and true.** Solo owners who leave HubSpot go to Pipedrive, Less Annoying
CRM, or Fluid CRM. What they value: a visual pipeline, fast setup, one flat price, no
upgrade traps. What kills adoption: data entry. One in three small businesses drop their
CRM inside a year; most use under half the features.

**Layer 2, what's new.** Attio, Folk, and Clay sell "AI-native" CRMs to startups at $29
to $69 per seat. None target a local trade owner. Tauri v2 is the 2026 default for
local-first desktop apps with a mobile path; Electron cannot reach phones.

**Layer 3, first principles.** The wedge nobody else has: Walker builds the owner's
website, so the quote form can feed the CRM directly. HubSpot cannot get inside that loop.

Eureka logged: "AI-first" is the wrong axis for this buyer. Competence and zero setup
win; AI is a settings toggle.

## Implementation alternatives (0C-bis, decided in D10)

Effort is given on both scales. "CC session" means one focused Claude Code build
session of a few hours. The CC column is the real plan; the human column is for
comparison only.

| Approach | Summary | Effort | Risk | Completeness | Decision |
|----------|---------|--------|------|--------------|----------|
| A | Rust core owns SQLite and all logic, typed commands, React UI | human ~10 wk / CC ~9 sessions | Med | 10/10 | Not chosen |
| B | JS owns schema, migrations, logic; thin Rust DB pipe; React UI | human ~8 wk / CC ~7 sessions | Low | 8/10 | **Chosen** |
| C | Port current vanilla JS into a Tauri shell | human ~2 wk / CC ~2 sessions | High (rewrite later) | 3/10 | Not chosen |

Consequences of B, stated plainly:
- Background work (the website lead poller, backups) runs only while the app is open,
  and only for the workspace that is open. A solo owner opens the app each morning; that
  is acceptable.
- The mobile path survives: the Rust pipe compiles for iOS and Android, and the UI is
  built with a phone layout in mind but ships desktop-only (minimum window 1024 px).
- If a true background service is ever needed, the repository interface is the seam to
  move logic into Rust.

## Accepted scope (v1)

### Core (19)

Each item lists what "done" means.

1. **Contacts.** First and last name, phones (many, typed: mobile, office), emails (many),
   address, company link, tags, source, custom fields (text, number, date, choice).
   Phone numbers normalised to E.164 on save; displayed in local format; unparseable
   numbers stored raw with a flag. Done: create, edit, archive, restore; a 10k-contact
   list scrolls smoothly (virtualised).
2. **Companies.** Name, phones, website, address, tags, notes, linked contacts and deals.
   Done: company page shows every contact, open and closed deal, and a merged timeline.
3. **Pipeline.** Deals with title, value, stage, position within stage, expected date,
   contact, company, source, won/lost reason. Board (drag between and within stages) and
   list. Stages editable, reorderable, colour-coded. Vocabulary setting: Deals, Jobs, or
   Quotes (labels only; the database always says `deals`). Deleting a stage with deals
   in it asks which stage to move them to first.
   Done: drag persists order and stage; keyboard move (shift+arrow); stage counts and
   value totals.
4. **Timeline.** Per contact, company, and deal. Entry types: note, call, email (logged
   manually), meeting, text, system (stage change, task done, import, lead received,
   merge). Done: add in two clicks; edit and delete user entries; system entries immutable.
5. **Tasks and follow-ups.** Title, optional due date, optional due time, linked record,
   done flag. `due_on` is always set when any due date exists; `due_at` is an optional
   refinement of it. Overdue means `due_at < now` when set, otherwise `due_on < today`;
   Today's buckets use `due_on`. Overdue rises to the top. Complete from the list without opening.
   Done: Today shows overdue, today, and next 7 days; snooze to tomorrow / next week.
6. **Today screen.** Sections: due now, new leads (last 7 days, no activity yet), gone
   quiet, recent activity, and, until a site is connected, one "connect your website"
   card that can be dismissed. Empty state is a designed screen, not a blank one.
7. **Instant search.** Cmd/Ctrl+K palette. External-content FTS5: a plain table
   `search_docs(rowid INTEGER PRIMARY KEY, entity_type, entity_id, text)` holds one row
   per searchable entity (a contact's row is rebuilt from contacts + phones + emails by
   triggers on those three tables; companies, deals, and activities each have their own
   triggers), and `search_index USING fts5(text, content='search_docs',
   content_rowid='rowid', tokenize='unicode61 remove_diacritics 2')` is kept in sync by
   the standard insert/update/delete triggers on `search_docs`. Queries join
   `search_index` to `search_docs` on rowid to get `entity_type, entity_id`. Triggers own
   `search_docs` entirely: each `AFTER INSERT/UPDATE` trigger deletes the entity's row and
   re-inserts it only `WHERE deleted_at IS NULL`, so soft delete removes it and restore
   brings it back with no repository code involved. Results grouped by type, keyboard
   navigable. Done: results in under 50 ms on 10k contacts + 50k notes.
8. **Quick add.** Cmd/Ctrl+N anywhere: one form with a type switcher. Required fields:
   contact = name; company = name; deal = title + stage (defaults to first); task =
   title; note = body + a record. Enter saves and closes; shift+Enter saves and clears
   for the next one.
9. **CSV import.** Drop a file or pick one (drops go through the file dialog on platforms
   where the dropped path is outside the app's file scope); detect delimiter, BOM, and
   encoding; map columns to fields with auto-guessing; preview 20 rows; dedupe policy
   (skip / update / create duplicates) keyed on email then phone. v1 imports contacts,
   and creates or links a company by exact name when a company column is mapped. Deals
   are not imported in v1 (TODO). The import runs inside one transaction (`db_begin` ...
   `db_commit`), sending batches of 500 rows as multi-row inserts through `db_batch`
   (which nests as a savepoint when a transaction is open), with a progress bar. While it
   runs, other writes queue behind the repository's write lock (the UI shows "queued
   behind the import") and the backup, lead-poll, and duplicate-scan timers pause. The
   result screen shows counts and
   offers "Save skipped rows as CSV" through a save dialog. Fixtures: HubSpot, Zoho,
   Pipedrive, Google Contacts, Excel exports, plus malformed files.
10. **Website quote-form leads.** Settings: site URL + token. The app polls
    `GET /api/crm/leads?after=<cursor>&limit=200` on the ClearPath site on launch and
    every 5 minutes while open, for the open workspace only. Response:
    `{ leads: [{ id, created_at, name, email, phone, service, message, page_url }],
    next_cursor }`. The site orders leads by `(created_at, id)` and produces an opaque
    cursor, `base64url("<created_at>|<id>")`, which it resolves as `created_at > X OR
    (created_at = X AND id > Y)`, so ties are never skipped. The app stores the cursor
    verbatim in `lead_sync.cursor`, mirrors it into `helix.json`, and passes it back as
    `after`; the laptop clock is never used. The request is made by a Rust command
    `leads_fetch(cursor, limit)` that reads `site_origin` from the open workspace's
    `settings` table and the token from the keychain under that workspace's uuid, so the
    token never enters the webview and the origin-token pairing stays in Rust. Each lead becomes
    a contact (deduped on email, then phone) plus a deal in the first stage with source
    "Website" and `external_id = "<site>:<lead id>"`, so a repeated poll is idempotent.
    A system timeline entry holds the original message. Site side: add the endpoint,
    bearer token, and a rate limit to the template (`server/routes.ts`), reading from the
    existing `leads` table.
11. **Gone-quiet detection.** Rule: an open deal whose `max(stage_entered_at, latest
    activity occurred_at)` is older than its stage's `quiet_days` (default 14, 0
    disables) surfaces on Today with one-tap "log a call" or
    "snooze a week". Contacts without deals are out of the rule in v1 (TODO: a
    settings-chosen tag with its own N).
12. **One-tap actions.** `tel:`, `sms:`, `mailto:`, and maps links from every phone,
    email, and address, opened through the OS opener. Each tap offers a one-click
    "log this" timeline entry.
13. **Saved views.** Any list's filters, sort, and columns can be named and pinned to the
    sidebar. Filters: stage, tag, source, value range, date ranges, custom fields.
14. **Reports.** Pipeline value by stage; won and lost this month, quarter, year; leads by
    source; conversion between stages; average days in stage. Built as SQL views over
    `deals` and `deal_stage_events` (every stage move is a row, so days-in-stage and
    conversion never need to mine the change log). Charts
    follow the dataviz skill; every chart has a table view.
15. **Duplicates and merge.** Scan on launch and every 24 hours while open, on normalised
    phone and email. "Possible duplicates" list; merge screen picks the surviving value
    per field, moves every activity, task, deal, tag, custom value, and attachment, and
    writes a system entry. Undo: 10-second toast, plus a Merges history screen that can
    reverse a merge for 30 days. Reversal restores the archived loser and re-points every
    row the merge moved (found by the merge's `batch_id`); the survivor's field values
    stay as they are now; reversal is refused, with a reason, if the survivor has been
    merged again since.
16. **Attachments and links.** Files are copied by the Rust command
    `copy_in(src) -> stored_name`, which computes the destination itself (the workspace's
    `attachments/` folder plus a UUID name) so JS never supplies a write path; the
    original name is kept in the row (drag-drop uses the dialog fallback as in item 9).
    Images show thumbnails served through Tauri's asset protocol, scoped to
    `workspaces/**/attachments/**`. Links are stored exactly as typed; no title fetch.
    Size cap 50 MB per file.
17. **Export and backup.** Export any list, or every entity as one CSV per entity inside a
    zip, plus a full JSON export. Automatic backup on launch (after first paint, skipped
    if any backup, including the pre-migration one, ran in the last hour) and every 6
    hours while open. Each backup is `VACUUM INTO` a temporary name then a rename, run on
    a second read-only connection so the UI never waits. Retention: every backup from the
    last 24 hours, then one per day for 30 days; Diagnostics shows total backup size.
    Backups cover the database only; attachments are plain files beside it and are
    documented as such. "Restore from backup" in settings calls `db_close` (which
    checkpoints and removes the `-wal` and `-shm` files), backs up today's file first,
    copies the chosen backup into place, then `db_open`s it; the confirmation names both
    dates. Export
    prefixes cells beginning with `= + - @ \t \r` with a quote to block spreadsheet
    formula injection.
18. **Undo and trash.** Every delete is a soft delete (`deleted_at`). Toast with Undo for
    10 seconds. Trash screen per type with restore. Permanent purge after 30 days, in this
    order: attachment files, `custom_values`, `tag_links`, `attachments` rows, then the
    row itself. Foreign keys carry the rest: `contact_phones`, `contact_emails`, and
    `deal_stage_events` are `ON DELETE CASCADE`; optional references (`contacts.company_id`,
    `deals.contact_id/company_id`, `activities.*_id`, `tasks.*_id`) are `ON DELETE SET
    NULL`. The search row was already removed by trigger at soft-delete time.
    `change_log` entries are kept.
19. **Settings.** Workspace-level: name, vocabulary, stages, tags, custom fields, currency
    and locale, backups, site connection, AI key and toggle. App-level (in
    `<appData>/helix.json`): workspace list with each workspace's last-polled and
    last-backup times (mirrored there on every poll and backup, since closed workspaces
    cannot be queried), last-opened workspace, theme (light/dark/auto), density
    (comfortable/compact), shortcuts. Plus a shortcuts sheet and Diagnostics.

### Accepted extras

- **E1, Optional AI module.** Settings: Anthropic API key stored in the OS keychain
  (`keyring` crate behind a custom command), model choice, "AI is on" toggle. Three
  actions: paste text (an email, a text, a voicemail transcript) and get a proposed
  contact + deal to confirm; draft a follow-up for a deal from its timeline, opened in
  the mail app; summarise a record. Each call sends only the record on screen. No
  background AI. When AI is off or the key is missing or rejected, the buttons stay
  visible but disabled, with a one-line reason and a link to settings. Requests go
  through `tauri-plugin-http` (Rust side), scoped to `https://api.anthropic.com/**`,
  which avoids the browser CORS block on the Anthropic API and keeps the CSP strict. The
  `AiProvider` base URL is overridable in the end-to-end build config
  (`tauri.e2e.conf.json`, merged with `--config`, which also allows `http://127.0.0.1:*`)
  so tests hit a local fake.
- **E7, Workspaces.** One SQLite file per business at
  `<appData>/workspaces/<uuid>/helix.db`, attachments and backups beside it. Sidebar
  switcher; create, rename, archive (archiving deletes the workspace's secrets from the
  keychain). Only the open workspace polls for leads and backs up; the switcher shows
  each workspace's last-polled and last-backup times from `helix.json`. Switching calls
  `db_close` then `db_open` and is blocked while an import or restore is running.

## Architecture

### Stack

- Tauri v2 with minimal capabilities. Plugins: `tauri-plugin-fs` scoped to the app data
  dir plus dialog-selected paths, `tauri-plugin-dialog`, `tauri-plugin-opener` (URLs and
  files; no shell plugin), `tauri-plugin-log`, `tauri-plugin-http` scoped to
  `https://api.anthropic.com/**` only (the site poll is a custom command, because the
  plugin's scope is static and the site origin is a runtime setting),
  `tauri-plugin-single-instance`. Asset protocol enabled and scoped to
  `workspaces/**/attachments/**` for thumbnails.
- **Database pipe (the D10 refinement).** Not `tauri-plugin-sql`. A small Rust module
  (`src-tauri/src/db.rs`, a few hundred lines) holds `Mutex<Option<rusqlite::Connection>>`
  and exposes, all as `#[tauri::command(async)]` so nothing runs on the main thread:
  `db_open(path)`, `db_close()` (runs `PRAGMA wal_checkpoint(TRUNCATE)` first),
  `db_query(sql, params) -> rows as arrays`, `db_execute(sql, params) -> changes`,
  `db_begin()`, `db_commit()`, `db_rollback()`, `db_batch(statements[])`, which runs
  the statements in a transaction when the connection is in autocommit mode and in a
  `SAVEPOINT`/`RELEASE` when a transaction is already open, rolling back on any error,
  and `db_backup(reason) -> path`, which derives `<workspace>/backups/<iso>-<reason>.db`
  from the open connection's path, opens a second `SQLITE_OPEN_READ_ONLY` connection,
  runs `VACUUM INTO` a `.tmp` name, renames, and returns the path (JS never supplies the
  destination). `db_close` waits for any in-flight `db_backup` to finish before it
  checkpoints and closes, so restore and workspace switch never race a backup on Windows.
  Any command while the connection is closed returns a named `DbClosed` error. After
  every `db_open` (launch, restore, switch) the app re-runs the boot sequence (FTS check,
  migrate) and clears the TanStack Query cache. Why not the
  stock plugin: it runs statements on an sqlx pool, so `BEGIN` and `COMMIT` can land on
  different connections and a read from the UI mid-import breaks the transaction. Because
  one connection serialises every caller, callers never see `SQLITE_BUSY`; they queue. The
  repository holds a JS-side write lock so a long transaction (import, merge, restore)
  queues other writes and pauses the backup, poll, and duplicate timers. Backups use a
  second read-only connection opened just for `VACUUM INTO`. Rows come back as arrays in
  select order, which is what Drizzle's proxy driver expects, and joins must alias
  duplicate column names (regression test included). `rusqlite` is pinned with the
  `bundled` feature (Windows has no system SQLite) and `better-sqlite3` is pinned to the
  same SQLite major for test parity. `PRAGMA journal_mode=WAL`, `foreign_keys=ON`,
  `busy_timeout=5000`.
- **Other Rust commands.** `secret_set/get/delete` over the `keyring` crate (v3 with
  `features = ["apple-native", "windows-native"]`, since it ships no default backend;
  async; service `helix`, user `<workspace-uuid>:anthropic` or `<workspace-uuid>:site`).
  `leads_fetch(cursor, limit)` via `reqwest`, reading the site origin from settings and
  the token from the keychain. `copy_in(src) -> stored_name` for attachments, destination
  computed in Rust.
- React 19, TypeScript, Vite. Router: wouter. Data: TanStack Query over a repository
  layer. Forms: react-hook-form + zod. UI primitives: Radix. Styling: Tailwind with Helix
  design tokens (from the fresh direction, D9). Charts: per the dataviz skill.
- Schema and migrations: Drizzle ORM (`sqlite-proxy` driver over `db_query`/`db_batch`),
  Drizzle Kit generates SQL migrations; the FTS5 tables and triggers and the
  `search_docs` rebuild triggers are hand-written custom migrations
  (`drizzle-kit generate --custom`, which registers them in `meta/_journal.json`). The
  JS migrator reads the journal, and for each pending file: runs `PRAGMA foreign_keys=OFF`
  through `db_execute` outside any transaction (inside one the pragma is a no-op), splits
  the file on `--> statement-breakpoint`, appends `INSERT INTO schema_migrations` as the
  last statement, applies the whole thing as one `db_batch` so the version is recorded in
  the same transaction as the migration, then runs `PRAGMA foreign_key_check` and
  `PRAGMA foreign_keys=ON`. A `db_backup("pre-migration")` runs first only when
  migrations are pending.
  Boot check: `SELECT sqlite_compileoption_used('ENABLE_FTS5')`.
- IDs: UUID v7 from the `uuid` package (`v7()`), never `crypto.randomUUID()` (v4 only).
- Tests: Vitest for pure logic; repository tests run through the same sqlite-proxy
  callback used in production, backed by `better-sqlite3` in Node, so the driver path is
  exercised. End-to-end: on Windows CI, WebdriverIO + `tauri-driver` + `msedgedriver`
  against the real app (a CI step reads the installed WebView2 version and downloads the
  matching driver; native file dialogs are not drivable, so a debug-only
  `HELIX_E2E_PICK=<path>` env var short-circuits the dialog wrapper); on macOS, Playwright
  against the Vite build started with `VITE_E2E=1`, whose entry registers
  `@tauri-apps/api/mocks` `mockIPC` before app boot, forwards every `db_*` call to a
  `page.exposeFunction` bound to `better-sqlite3` in the Playwright Node process (reusing
  the repository test harness), and stubs every other command (`plugin:dialog|*`,
  `plugin:fs|*`, `plugin:opener|*`, `plugin:log|*`, `secret_*`, `leads_fetch`, `copy_in`)
  with no-op or fixture responses. The Mac run skips restore, workspace switch, and
  attachments. A manual real-app checklist runs on Mac before each release (tauri-driver
  has no macOS support).
- CI: GitHub Actions, `tauri-action`, matrix macOS (arm64, x64) + Windows (x64). Unsigned
  artifacts in v1 (TODO E5).

runs zod validation. Repository joins alias every column.

### Data model (one SQLite file per workspace)

Common columns on every entity table: `id TEXT PRIMARY KEY` (UUID v7),
`created_at`, `updated_at` (ISO 8601 UTC), `deleted_at NULL`.

```
  contacts(id, first_name, last_name, company_id?, address_json, source_id?, notes)
  contact_phones(id, contact_id, raw, e164?, label, is_primary)
  contact_emails(id, contact_id, email_lower, label, is_primary)
  companies(id, name, website, phone_e164, address_json, source_id?, notes)
  pipelines(id, name)                        -- one row in v1; table exists for later
  stages(id, pipeline_id, name, position, color, quiet_days, is_won, is_lost)
  deals(id, title, value_cents, currency, stage_id, stage_entered_at, position,
        contact_id?, company_id?, source_id?, external_id?, expected_on?, closed_at?,
        outcome_reason?)
  deal_stage_events(id, deal_id, from_stage_id?, to_stage_id, at)   -- one row per move
  activities(id, kind, body, occurred_at, contact_id?, company_id?, deal_id?,
             is_system, actor_id)
  tasks(id, title, due_on?, due_at?, done_at?, contact_id?, company_id?, deal_id?)
  tags(id, name, color); tag_links(tag_id, entity_type, entity_id)
  custom_fields(id, entity_type, name, kind, options_json, position)
  custom_values(field_id, entity_id, value_text, value_num, value_date)
  attachments(id, entity_type, entity_id, file_name, stored_name, bytes, mime)
  sources(id, name, kind)                    -- Website, Referral, Import, Manual, ...
  saved_views(id, entity_type, name, query_json, position, pinned)
  settings(key, value_json)                  -- workspace-level keys only
  lead_sync(site_origin, cursor TEXT, last_polled_at, last_error)   -- cursor is opaque
  schema_migrations(version, applied_at)
  change_log(id, at, actor_id, entity_type, entity_id, op, before_json, after_json, batch_id)
  search_docs(rowid INTEGER PK, entity_type, entity_id, text)   -- rebuilt by triggers
  search_index  (FTS5 external content over search_docs.text; unicode61 remove_diacritics 2)
```

No unique constraint on email or phone: duplicates are allowed by policy (import
"create duplicates") and surfaced by the duplicates scan. Creating a contact whose email
or phone already exists shows an inline "already exists, open it?" warning, not an error.
`actor_id` is a single fixed value in v1 ("owner"); it exists so team mode is additive.

### State machines

```
  DEAL:   [open in stage S] --drag/move--> [open in stage S'] --stage.is_won--> [won]
              |                                                   |
              +--stage.is_lost--> [lost, reason required]         +--reopen--> [open]
          Invalid: move to a stage in another pipeline (repository checks
          stage.pipeline_id matches; v1 has one pipeline so this cannot occur in the UI).
          Invalid: delete stage with deals (UI forces a target stage first).

  TASK:   [open] --check--> [done, done_at set] --uncheck--> [open]
          [open] --snooze--> [open, due moved]
          Overdue is derived (due < today and not done), never stored.

  IMPORT: [file picked] -> [parsed] -> [mapped] -> [previewed] -> [running: db_begin,
             write lock held, timers paused, one db_batch (savepoint) per 500 rows]
             -> [db_commit] | [db_rollback, error shown]
          Closing the window during [running] rolls back (transaction never committed).

  LEAD POLL: [idle] --timer/launch--> [fetching] --200--> [applying, tx] --> [idle, cursor saved]
             --401/403--> [auth error, banner, timer stopped until settings change]
             --network--> [idle, retry with backoff 1,2,4,8 min, banner after 3 failures]
```

### Data flows with shadow paths

**CSV import**
```
  happy:  file -> parse -> map -> preview -> tx: batches of 500 (dedupe, upsert) -> commit -> report
  nil:    no file chosen -> nothing happens (dialog cancelled)
  empty:  0 data rows -> "This file has headers but no rows" screen, no tx opened
  error:  parse fails (bad encoding, ragged rows) -> ImportParseError with row number;
          db_batch error mid-run -> rollback, ImportWriteError, nothing partially imported
```

**Website lead poll**
```
  happy:  timer -> GET after=cursor -> {leads, next_cursor} -> tx: per lead, skip if
          external_id exists, else dedupe contact, create deal, system activity -> commit
          -> save cursor
  nil:    no site configured -> poller never starts; Today shows the connect card once
  empty:  200 {leads: [], next_cursor: same} -> last_polled_at=now, no UI change
  error:  401/403 -> LeadPollAuthError banner; 5xx/timeout -> backoff, banner after 3
```

**Quick add**
```
  happy:  Cmd+N -> form -> validate -> repository.create -> query invalidate -> toast + undo
  nil:    submit with empty required field -> inline error, focus moved, nothing written
  empty:  whitespace-only name -> trimmed and treated as empty
  error:  import or merge in progress -> the write queues behind the write lock, toast
          "Saved, queued behind the import"; database closed (restore or switch in
          progress) -> DbClosedError toast; any other SQLite error -> WriteError toast
```

**AI paste-to-record (E1)**
```
  happy:  paste -> POST via tauri-plugin-http with JSON schema -> proposed contact+deal
          -> user edits -> confirm -> create
  nil:    AI off or no key -> button disabled with reason and settings link
  empty:  empty paste -> button disabled
  error:  401 -> AiKeyRejected (link to settings); 429/5xx -> AiRequestError with retry;
          malformed JSON from model -> AiParseError, raw text shown so nothing is lost
```

## Security and threat model

- Tauri capabilities: only the plugins listed; fs scoped to the app data dir plus
  dialog-selected paths; opener limited to `https:`, `mailto:`, `tel:`, `sms:` URLs and
  files inside the workspace folder. CSP: `default-src 'self'; img-src 'self' asset:
  http://asset.localhost data:; style-src 'self' 'unsafe-inline'` (Radix and React set
  inline styles); `connect-src 'self'` only, since network calls run on the Rust side
  (`tauri-plugin-http` scoped to the Anthropic API; `leads_fetch` for the site). No
  remote code, no CDN fonts; the app works offline.
- Secrets (site token, Anthropic key) in the OS keychain (macOS Keychain, Windows
  Credential Manager) via the `keyring` crate, never in SQLite or `helix.json`. Known
  gotcha: unsigned macOS builds change identity per build, so the Keychain prompt
  reappears after each dev rebuild until E5 lands; documented in CONTRIBUTING. A
  dev-only in-memory store is gated behind an env flag and cannot compile into release.
- All SQL parameterised through Drizzle. FTS queries quote user input.
- CSV export: formula-injection guard on cells starting with `= + - @ \t \r`.
- Attachments: copied into the workspace folder via `copy_in(src)`, which chooses the
  destination in Rust with a UUID name; JS never supplies a write path; original path
  never trusted; opened only through the OS opener.
- Website endpoint: bearer token per site, HTTPS only, cursor bounded, `limit` capped at
  200, rate limited on the site, returns only lead fields. Token rotation from the site
  admin.
- AI: only explicit user actions, only the visible record, key never logged. The model's
  output is untrusted data: shown for confirmation, never auto-saved, never executed.
- Local threat: the SQLite file is unencrypted on disk (same as the owner's other
  documents). Full-disk encryption is the OS's job; documented in README. Encrypted
  workspaces are a TODO.

## Edge cases

- 47-character names, one-word names, other scripts: no truncation in lists (ellipsis
  with a title tooltip); search handles diacritics via `unicode61 remove_diacritics`.
- Phone formats: `801.555.0100`, `(801) 555-0100`, `+1 801 555 0100` normalise to the
  same E.164 for dedupe; unparseable numbers stored raw with `e164 = NULL`, never rejected.
- Zero states: every list, Today, reports, and search have a designed empty state with
  the one action that fills it.
- Big imports: 50k rows in one transaction, batches of 500 multi-row inserts, progress
  bar, UI responsive (`await` between batches).
- App closed mid-write: WAL + transactions; nothing half-written.
- Second launch: the single-instance plugin focuses the running window.
- Disk full: backups fail loudly; writes fail with WriteError, never silently.
- Restore over live data: confirmation names the backup date and today's date; today's
  file is backed up first; the database is closed during the copy.
- Stage deleted with deals: forced move dialog. Vocabulary change: labels only.
- Merge: 10-second undo toast, 30-day reversal from the Merges history screen.
- Time zones and dates: `due_on` and `expected_on` are dates without time;
  `occurred_at` and `due_at` are UTC and shown local.
- Workspace switch while an import or restore runs: blocked with a message.
- Launch order: open DB, check FTS5, migrate (blocks first paint), then paint Today, then
  in the background: backup, duplicate scan, lead poll.

- Repository functions are the only place SQL lives. One file per entity.
- Normalisers (`phone.ts`, `email.ts`, `csv.ts`) are pure and unit-tested first.
- No `any`. zod schemas are the source of truth for both forms and repository input.
- Components under 200 lines; screens compose components.
- ASCII diagrams in the headers of `migrator.ts`, `import/service.ts`, `leads/poller.ts`,
  and `src-tauri/src/db.rs`.

## Performance

Targets on a 2019 laptop: first paint under 1.5 s (only migration blocks it); 10k
contacts list virtualised; search under 50 ms; import 10k rows under 20 s (about 20
`db_batch` calls of 500 multi-row inserts, not 60k statements). Indexes on every FK,
`email_lower`, `e164`, `stage_id`, `stage_entered_at`, `position`, `due_on`,
`deleted_at`, `external_id`, `deal_stage_events(deal_id, at)`. FTS5 kept in sync by
triggers.

## Observability

`tauri-plugin-log` to a rotating file in the app data dir (7 days). Diagnostics screen:
app version, data path, DB size, last backup time, last lead poll result and cursor,
migration version, FTS5 status, copy-log button, "reveal data folder". No telemetry, no
crash upload in v1. Every service logs start, end, counts, and named errors.

## Deployment

- GitHub Actions builds on tag: `.dmg` (arm64, x64) and `.msi`/`.exe`. Release notes from
  the changelog. Unsigned in v1: README documents the right-click-open on Mac and
  SmartScreen "more info" on Windows, and the repeated Keychain prompt. This blocks

  Windows VM (UTM or Parallels) before each release.

## Long-term trajectory

- Sync: `change_log` + UUID v7 + `updated_at` + soft deletes + `actor_id` make a sync

- Mobile: Tauri v2 iOS/Android with the same Rust pipe; UI needs a phone layout, data

- Teams: `actor_id` becomes real; no schema rewrite.

- Trajectory risk: if background work becomes essential (sync, always-on polling), the

## Design and UX (D9: fresh direction)

Research brief for the design skills at execution time:
- Audience: owners 40 to 65, on a laptop in a truck or at a kitchen table, often two-finger
  typists, who already trust QuickBooks, Google, and their bank's app.
- What they scan for: their customer's name and money in large type; what's due; the
  phone number.
- Hierarchy: Today first; on a record, the phone and the next step above everything else.
- Type: system fonts, larger default (16 px body), tabular numbers for money.
- Colour: one meaningful accent for "needs you", a separate stage ramp, no cream/serif
  defaults, no near-black-with-acid-green.
- Density: comfortable default, compact toggle. Minimum window width 1024 px.
- Every interaction designed with edge cases: long names, zero results, offline.
- Trust: no dark patterns, no "upgrade" prompts anywhere, plain confirmations.
- Deliverable before code: a direction contract and comps for Today, Contact, Pipeline,
  Import, and Empty states; then a design review pass with screenshots at 1024, 1280,
  and 1440 widths.
